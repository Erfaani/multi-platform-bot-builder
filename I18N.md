# INTERNATIONALIZATION & LOCALIZATION

Status: **Phase 0 — strategy** · Locales: `fa` (RTL), `en` (LTR) · Last updated: 2026-08-10

The rule that governs everything here: **no user-facing string is ever a literal in business
logic.** Not in a service, not in a feature handler, not in a bot reply. Only keys.

---

## 1. Two kinds of translatable content

| Kind | Examples | Mechanism |
|---|---|---|
| **Static** — ships with the code | UI labels, error messages, email subjects, bot system messages | `gettext` catalogs (backend) · `next-intl` message files (frontend) |
| **Dynamic** — lives in the database | Template names, feature descriptions, payment instructions, a customer's own welcome message and menu | `i18n_content.Translation` side table |

Mixing these up is the usual cause of a half-translated product, so they are kept
structurally separate.

### Static

Backend: `backend/locale/{fa,en}/LC_MESSAGES/django.po`, `gettext_lazy` at module level.
Frontend: `frontend/messages/{fa,en}.json`, ICU message format for plurals and interpolation.

Key namespaces (spec §5):

```
bot.appointment.select_doctor
bot.order.payment_pending
dashboard.my_bots
checkout.total_price
error.order.invalid_transition
email.payment_approved.subject
```

Rules: keys are dot-namespaced by surface (`bot.` / `dashboard.` / `checkout.` / `error.` /
`email.`), never reused across surfaces, never assembled by string concatenation at runtime
(that breaks extraction and RTL both). CI fails on a missing key in any active locale and on
an unused key.

### Dynamic

```python
translation(content_type, object_id, field, locale, value)
# unique (content_type, object_id, field, locale)
```

Resolution chain — first hit wins:

```
requested locale → tenant/bot default locale → platform default locale → source value
```

For per-bot messages there is an extra layer in front:

```
bot override → template default → feature default → platform default
```

So a clinic can rewrite its own welcome message in Persian without touching English, and
anything unwritten still renders correctly.

## 2. Locale resolution order

**Web:** explicit URL prefix (`/fa/…`, `/en/…`) → authenticated user's `preferred_locale` →
cookie → `Accept-Language` → platform default.
A manual switch writes to the user profile (spec §5) and the cookie.

**Bots:** the bot session's stored locale → the end user's `language_code` from the platform
update → the bot's `default_locale` → platform default. An end user can switch language from
the bot menu; the choice persists on their `bot_session` and `business_contact`.

**Emails and notifications** use the recipient's stored `preferred_locale`, resolved at send
time, not at enqueue time.

## 3. Direction and typography

- `dir` is derived from the locale (`fa → rtl`, `en → ltr`) and set on `<html>`.
- Layout uses **logical CSS properties only** — `margin-inline-start`, `padding-inline`,
  `inset-inline-start`. No `left`/`right` in component styles; a lint rule enforces it.
  Tailwind's logical utilities (`ms-`, `me-`, `ps-`, `pe-`, `start-`, `end-`) are the default.
- Icons with direction (arrows, chevrons, progress) mirror in RTL; logos and media do not.
- Fonts: **Vazirmatn** for Persian, **Inter** for English, self-hosted (no external CDN),
  subset and preloaded. Persian gets slightly increased line-height for legibility.
- Persian text handling: ZWNJ (`‌`) preserved in input and storage; Arabic `ي`/`ك`
  normalised to Persian `ی`/`ک` on save; Persian and Arabic-Indic digits normalised to ASCII
  before any numeric parsing.
- Bidi safety: user-generated content interpolated into a message is wrapped in isolates
  (`⁨…⁩`) so a Persian business name cannot scramble an English sentence around it.

## 4. Numbers, dates, currency

- **Numbers**: Persian digits for display in `fa`, ASCII in `en`; thousands separators per
  locale. Storage and transport are always ASCII.
- **Dates**: all instants stored UTC. `fa` renders the **Jalali (Shamsi)** calendar; `en`
  renders Gregorian. Conversion happens in the presentation layer only — no Jalali value is
  ever persisted.
- **Timezones**: rendered in the user's (or the business's) timezone. Appointments also store
  the `business_timezone` in effect at booking so a later tz/DST change cannot silently move
  a confirmed slot.
- **Currency**: formatted from `amount_minor` + `currency` + the currency's `exponent`,
  with locale-correct symbol placement.
  **Toman is a display unit, not a currency** — IRR is stored, and `fa` displays
  `amount / 10` with a "تومان" suffix. The divisor lives in the `currency` table, so nothing
  is hard-coded.

```
IRR  49_000_000 minor  →  fa: «۴٬۹۰۰٬۰۰۰ تومان»   en: "IRR 49,000,000"
USD        14_900      →  en: "$149.00"            fa: «۱۴۹٫۰۰ دلار»
USDT  149_000_000      →  "149.00 USDT"            (exponent 6)
```

Formatting exists in exactly one place per stack (`core.formatting` / `lib/format.ts`).
Ad-hoc formatting in a component or a bot reply is a review rejection.

## 5. Localized experience defaults

Locale, country and currency are independent, but the platform proposes sensible defaults
(spec §43) that the user can always override:

| Signal | Locale | Currency | Payment methods offered |
|---|---|---|---|
| Country = IR | `fa` | IRR (shown as Toman) | manual card transfer |
| Otherwise | `en` | USD | USDT / BTC / ETH |

Payment method availability is driven by `payment_method.country_scope` and `currency` — it
is admin data, not code.

---

## 6. Operational rules

- Adding a locale = adding a `.po` + a `messages/*.json` + a `currency`/formatting entry.
  **No code change.** The list of active locales is a setting.
- Translation keys are part of the API contract: error responses carry both a stable
  machine `code` and a localized `message`.
- Admins can edit dynamic translations from the admin panel (spec §25, `admin/translations/`)
  without a deployment.
- Untranslated dynamic content falls back rather than showing an empty string — a blank
  business name is worse than an untranslated one.
- Pseudo-locale (`en-XA`) available in development to surface hard-coded strings and layouts
  that break on longer text.
